1. Fundamentos do Domínio de Pagamentos & Precisão Numérica

Em sistemas financeiros, a automação de testes não se limita a asserções de status HTTP 200. Falhas lógicas em APIs de pagamento geram passivos contábeis diretos, perdas de liquidação, vulnerabilidades a fraudes e severas sanções aplicadas pelo Banco Central do Brasil (BACEN) e pelo PCI Security Standards Council.

1.1 Os Atores do Arranjo de Pagamentos

[Portador do Cartão / Pagador] │ ▼ [Gateway / PSP] ───────► [Motor de Risco / Antifraude] │ ▼ [Adquirente] (ex: Cielo, Stone, Rede, PagBank) │ ▼ [Bandeira] (ex: Visa, Mastercard, Elo) │ ▼ [Banco Emissor] (ex: Nubank, Itaú, Bradesco)
  • Gateway: Integrador puramente técnico que recebe os dados da aplicação web/mobile, tokeniza, criptografa e distribui às pontas adquirentes sem liquidar valores.
  • PSP (Payment Service Provider): Plataforma agregadora que unifica gateway, conciliação e liquidação financeira sob uma mesma licença contratual (ex: Pagar.me, Asaas, Stripe).
  • Adquirente: Entidade credenciada pelas bandeiras para habilitar estabelecimentos comerciais e processar a captura e liquidação financeira das transações.
  • Bandeira: Define as regras operacionais globais de segurança, roteamento, compensação e limites das transações.
  • Emissor: Instituição financeira que concede o limite de crédito ou custodia a conta corrente do comprador, aprovando ou recusando a transação conforme saldo e risco comportamental.

1.2 Máquina de Estados Finitos (FSM) da Transação

O ciclo de vida de uma cobrança com cartão é governado por uma Máquina de Estados Finitos com transições determinísticas. Um QA precisa testar exaustivamente não apenas as transições válidas, mas também a rejeição de transições inválidas (ex: tentar capturar uma transação já cancelada):

[Iniciada] ──► [Autorizada] ──► [Capturada] ──► [Liquidada] │ │ │ ▼ ▼ ▼ [Recusada] [Cancelada] [Estornada (Refund)] │ ▼ [Disputa / Chargeback]
Operação Definição Técnica Efeito Contábil no Sistema
Autorização (Auth) Valida a integridade do cartão, limite disponível e aprovação no emissor. Bloqueia o limite do portador. Nenhum dinheiro trocou de mãos ainda.
Captura (Capture) Confirmação da transação pelo lojista para efetivação contábil do débito. Lança a compra na fatura do cliente e programa o recebível futuro do lojista.
Cancelamento (Void) Anulação da reserva de saldo antes do fechamento diário do lote bancário. Desfaz a pré-autorização imediatamente sem cobrança na fatura.
Estorno (Refund) Devolução do valor após a transação já ter sido capturada e consolidada. Dispara a liquidação reversa entre emissor e adquirente; pode ser total ou parcial.

1.3 O Perigo do Ponto Flutuante (IEEE 754) em Sistemas Financeiros

Processadores modernos representam frações decimais na memória através da norma binária IEEE 754. Operações triviais como 0.1 + 0.2 resultam na dízima binária finita 0.30000000000000004. Em gateways que processam milhões de transações por hora, pequenas discrepâncias fracionárias acumulam rombos contábeis massivos.

Regra Fundamental para Automação de APIs APIs de pagamento devem operar com inteiros na menor fração da moeda (ex: amountInCents: 1000 para R$ 10,00) ou strings numéricas de precisão fixa. O framework de testes do QA deve validar que payloads contendo números decimais do tipo 10.99 sejam prontamente rejeitados com 400 Bad Request ou 422 Unprocessable Entity.

2. Redes, Protocolo HTTP & Rastreabilidade Distribuída

Para atuar com autonomia no dia a dia, o QA deve dominar a camada de transporte, a semântica rigorosa dos códigos HTTP e como auditar microsserviços via rastreamento distribuído.

2.2 Matriz de Status Codes e Semântica de Negócio

Status Code Cenário Semântico em Pagamentos Conduta Correta do QA na Automação
400 Bad Request Payload mal formatado, sintaxe JSON corrompida ou tipos de dados inválidos. Asserir quando tipos primitivos estiverem violados (ex: string em campo numérico).
422 Unprocessable Entity Sintaxe válida, mas violação de regra de negócio (ex: data de expiração no passado, estorno maior que saldo). Asserir mensagem de erro amigável e código de erro de domínio específico.
401 Unauthorized Token ausente, inválido ou expirado. Validar que nenhum detalhe de infraestrutura vaze no body da resposta.
403 Forbidden Autenticado com sucesso, mas sem autorização de acesso ao recurso solicitado. Testar cenários de permissão e isolamento de tenants (Lojista A acessando recurso B).
409 Conflict Conflito de estado do recurso (ex: reutilizar Idempotency-Key com payload modificado). Validar que a transação original seja preservada intacta sem alteração de valores.
502 / 504 Gateway Error Instabilidade ou timeout ao conectar com a adquirente ou autorizador externo. Validar que o gateway ative políticas de retentativa, fallback ou circuito aberto (Circuit Breaker).

2.3 Rastreabilidade Distribuída (Distributed Tracing)

Em ambientes de microsserviços, quando um pagamento falha, o QA precisa auditar exatamente onde o fluxo foi interrompido. Toda requisição enviada pelo framework de testes automatizados deve injetar headers de correlação padronizados:

  • X-Correlation-ID ou X-Request-ID: Identificador único UUIDv4 que deve ser propagado por todos os microsserviços internos e retornado no cabeçalho de resposta HTTP.
  • traceparent (Padrão W3C Trace Context): Permite correlacionar spans de observabilidade no OpenTelemetry, Datadog ou Jaeger.

4.3 Service Object Pattern: BaseClient e PaymentClient

src/clients/BaseClient.tsTypeScript
import { APIRequestContext, APIResponse } from '@playwright/test';
import { randomUUID } from 'node:crypto';

export abstract class BaseClient {
  protected constructor(
    protected readonly request: APIRequestContext,
    protected readonly baseURL: string
  ) {}

  protected async get(endpoint: string, headers?: Record<string, string>): Promise<APIResponse> {
    return this.request.get(`${this.baseURL}${endpoint}`, {
      headers: {
        'X-Correlation-ID': randomUUID(),
        ...headers,
      },
    });
  }

  protected async post(
    endpoint: string,
    data: unknown,
    headers?: Record<string, string>
  ): Promise<APIResponse> {
    return this.request.post(`${this.baseURL}${endpoint}`, {
      data,
      headers: {
        'Content-Type': 'application/json',
        'X-Correlation-ID': randomUUID(),
        ...headers,
      },
    });
  }
}
src/clients/PaymentClient.tsTypeScript
import { APIRequestContext, APIResponse } from '@playwright/test';
import { BaseClient } from './BaseClient';
import { CreatePaymentDTO, RefundRequestDTO } from '../models/payment.types';

export class PaymentClient extends BaseClient {
  constructor(request: APIRequestContext, baseURL: string) {
    super(request, baseURL);
  }

  async createPayment(
    payload: CreatePaymentDTO,
    options?: { idempotencyKey?: string; token?: string }
  ): Promise<APIResponse> {
    const headers: Record<string, string> = {};
    if (options?.idempotencyKey) {
      headers['Idempotency-Key'] = options.idempotencyKey;
    }
    if (options?.token) {
      headers['Authorization'] = `Bearer ${options.token}`;
    }
    return this.post('/v1/payments', payload, headers);
  }

  async capture(id: string, token: string, amountInCents?: number): Promise<APIResponse> {
    return this.post(`/v1/payments/${id}/capture`, { amountInCents }, {
      Authorization: `Bearer ${token}`,
    });
  }

  async refund(id: string, payload: RefundRequestDTO, token: string): Promise<APIResponse> {
    return this.post(`/v1/payments/${id}/refund`, payload, {
      Authorization: `Bearer ${token}`,
    });
  }
}

5. Cenários Críticos: Idempotência, Concorrência & Estornos

5.1 Idempotência: Replays & Prevenção de Adulteração

O cabeçalho Idempotency-Key garante que falhas de rede no cliente não resultem em cobranças duplicadas ao reenviar a mesma transação. Adicionalmente, a reutilização de uma chave pré-existente com corpo adulterado deve resultar em conflito explícito.

tests/payments/idempotency.spec.tsTypeScript
import { test, expect } from '../../src/fixtures/apiFixtures';
import { PaymentFactory } from '../../src/factories/PaymentFactory';
import { faker } from '@faker-js/faker';

test.describe('Validação de Idempotência em Transações', () => {
  test('deve retornar a mesma transação original sem duplicar cobrança', async ({
    paymentClient,
    merchantToken,
  }) => {
    const idempotencyKey = faker.string.uuid();
    const payload = PaymentFactory.createValidCreditCardPayload();

    // 1ª Requisição
    const res1 = await paymentClient.createPayment(payload, { idempotencyKey, token: merchantToken });
    expect(res1.status()).toBe(201);
    const body1 = await res1.json();

    // 2ª Requisição (Replay idêntico)
    const res2 = await paymentClient.createPayment(payload, { idempotencyKey, token: merchantToken });
    expect([200, 201]).toContain(res2.status());
    const body2 = await res2.json();

    expect(body2.id).toBe(body1.id);
  });

  test('deve retornar 409 Conflict ao reutilizar chave com payload adulterado', async ({
    paymentClient,
    merchantToken,
  }) => {
    const idempotencyKey = faker.string.uuid();
    const original = PaymentFactory.createValidCreditCardPayload({ amountInCents: 5000 });
    const tampered = PaymentFactory.createValidCreditCardPayload({ amountInCents: 9900 });

    await paymentClient.createPayment(original, { idempotencyKey, token: merchantToken });
    const resTampered = await paymentClient.createPayment(tampered, { idempotencyKey, token: merchantToken });

    expect([409, 422]).toContain(resTampered.status());
  });
});

5.2 Teste de Concorrência e Double-Spending via Promise.all

Simulação de ataque de corrida (Race Condition) disparando múltiplas requisições simultâneas no mesmo milissegundo pelo Event Loop do Node.js:

tests/payments/concurrency.spec.tsTypeScript
import { test, expect } from '../../src/fixtures/apiFixtures';
import { PaymentFactory } from '../../src/factories/PaymentFactory';

test('não deve permitir cobrança dupla ao disparar requisições concorrentes no mesmo milissegundo', async ({
  paymentClient,
  merchantToken,
}) => {
  const payload = PaymentFactory.createValidCreditCardPayload();
  const fixedKey = `race-${Date.now()}`;

  // Dispara 5 requisições em paralelo real
  const promises = Array.from({ length: 5 }).map(() =>
    paymentClient.createPayment(payload, { idempotencyKey: fixedKey, token: merchantToken })
  );

  const responses = await Promise.all(promises);
  const statuses = responses.map((r) => r.status());

  // Invariante: Estritamente UMA requisição pode retornar 201 Created
  const creations = statuses.filter((s) === 201);
  expect(creations.length).toBe(1);

  // As demais devem ser idempotentes (200) ou bloqueadas por lock concorrente (409)
  const allSafe = statuses.every((s) => [200, 201, 409].includes(s));
  expect(allSafe).toBe(true);
});

5.3 Estornos Parciais Cumulativos (Prevenção de Saldo Negativo)

Garante que a soma dos estornos parciais nunca exceda o montante total capturado originalmente.

tests/payments/cumulative-refund.spec.tsTypeScript
import { test, expect } from '../../src/fixtures/apiFixtures';
import { PaymentFactory } from '../../src/factories/PaymentFactory';

test('deve permitir estornos até o teto capturado e rejeitar excedente com 422', async ({
  paymentClient,
  merchantToken,
}) => {
  // 1. Cria e captura cobrança de R$ 100,00 (10000 centavos)
  const payload = PaymentFactory.createValidCreditCardPayload({ amountInCents: 10000 });
  const authRes = await paymentClient.createPayment(payload, { token: merchantToken });
  const { id } = await authRes.json();
  await paymentClient.capture(id, merchantToken, 10000);

  // 2. Primeiro estorno parcial: R$ 60,00 (6000 centavos)
  const refund1 = await paymentClient.refund(id, { amountInCents: 6000 }, merchantToken);
  expect(refund1.status()).toBe(200);

  // 3. Segundo estorno parcial: R$ 40,00 (4000 centavos - atinge 100% do saldo)
  const refund2 = await paymentClient.refund(id, { amountInCents: 4000 }, merchantToken);
  expect(refund2.status()).toBe(200);

  // 4. Terceiro estorno de R$ 0,01 -> Rejeição obrigatória
  const refund3 = await paymentClient.refund(id, { amountInCents: 1 }, merchantToken);
  expect(refund3.status()).toBe(422);
  const errData = await refund3.json();
  expect(errData.code).toBe('REFUND_AMOUNT_EXCEEDS_AVAILABLE_BALANCE');
});

6. Split de Pagamentos & Regras Contábeis de Marketplace

Em arquiteturas de marketplace, a API realiza a partilha dos valores entre múltiplos recebedores (vendedores), retém a comissão da plataforma e atribui quem absorve o MDR (Merchant Discount Rate) e o risco de chargeback.

tests/payments/split-payment.spec.tsTypeScript
import { test, expect } from '../../src/fixtures/apiFixtures';

test('deve validar integridade contábil em split com comissão e taxa de processamento', async ({
  request,
  merchantToken,
}) => {
  const payload = {
    amountInCents: 20000, // R$ 200,00
    currency: 'BRL',
    paymentMethod: 'CREDIT_CARD',
    splitRules: [
      {
        recipientId: 'rec_vendedor_externo',
        percentage: 85, // R$ 170,00
        chargeProcessingFee: false,
        liableForChargeback: true,
      },
      {
        recipientId: 'rec_marketplace_taxa',
        percentage: 15, // R$ 30,00
        chargeProcessingFee: true, // Plataforma absorve a taxa
        liableForChargeback: false,
      },
    ],
  };

  const res = await request.post('/v1/payments', {
    headers: { Authorization: `Bearer ${merchantToken}` },
    data: payload,
  });

  expect(res.status()).toBe(201);
  const body = await res.json();

  // Invariante: O somatório das divisões líquidas não pode exceder o valor bruto da transação
  const totalAllocated = body.split.reduce(
    (acc: number, cur: any) => acc + cur.netAmountInCents,
    0
  );
  expect(totalAllocated).toBeLessThanOrEqual(20000);

  const vendor = body.split.find((s: any) => s.recipientId === 'rec_vendedor_externo');
  expect(vendor.netAmountInCents).toBe(17000);
});

7. Banco de Dados: Do Zero Absoluto à Auditoria de Pagamentos

Para um QA de backend e pagamentos, o banco de dados é a Fonte Única da Verdade (Single Source of Truth). Não basta que a API responda 200 OK no endpoint; se os dados gravados no banco estiverem incorretos, o dinheiro não fecha no final do dia. Este capítulo explica tudo o que você precisa saber sobre bancos relacionais, mesmo que nunca tenha aberto um terminal de banco na vida.

7.1 O que é um Banco de Dados Relacional?

Pense em um banco de dados relacional (RDBMS como PostgreSQL ou MySQL) como um conjunto de planilhas superpoderosas e conectadas entre si, porém com regras de segurança rígidas que impedem corrupção de dados.

BANCO DE DADOS: "fintech_db" │ ├── TABELA: "customers" (Clientes) │ [id (PK)] │ [nome] │ [email] │ [saldo_centavos] │ cust_01 │ Maria Silva │ maria@email.com │ 50000 │ cust_02 │ João Souza │ joao@email.com │ 12000 │ └── TABELA: "transactions" (Transações) [id (PK)] │ [customer_id (FK)] ──► Aponta para "customers.id" tx_991 │ cust_01 │ R$ 100,00 │ AUTHORIZED tx_992 │ cust_01 │ R$ 40,00 │ CAPTURED tx_993 │ cust_02 │ R$ 120,00 │ FAILED
  • Tabela: Uma entidade de negócio (ex: transactions, customers, refunds). É a "aba" da planilha.
  • Coluna / Campo: O atributo que define um tipo específico de dado (ex: amount_in_cents só aceita números inteiros).
  • Linha / Registro / Tupla: O registro individual de um evento ocorrido (ex: os dados da transação específica número 991).
  • Chave Primária (Primary Key - PK): O identificador único e exclusivo daquela linha (ex: UUID ou ID sequencial). Nunca pode haver dois registros com a mesma PK.
  • Chave Estrangeira (Foreign Key - FK): O elo que liga uma tabela à outra. Se a transação possui customer_id = 'cust_01', o banco só aceita salvar essa transação se cust_01 existir na tabela customers. Isso se chama Integridade Referencial.

7.2 Dicionário de Tipos de Dados Cruciais em Finanças

Tipo SQL O que armazena? Uso Correto em Pagamentos
INTEGER / BIGINT Números inteiros sem vírgula. Valores monetários em centavos (R$ 10,00 = 1000). Evita erros de arredondamento.
NUMERIC(15, 2) / DECIMAL Números com precisão exata de casas decimais. Usado em relatórios contábeis e taxas percentuais (ex: taxa MDR de 2.49%).
VARCHAR(n) / TEXT Textos e strings alfanuméricas. IDs de adquirentes, nomes, mensagens de erro e dados mascarados (firstSixDigits).
UUID Identificadores únicos universais (128 bits). Padrão da indústria para IDs de transações públicas (ex: c8e5d3f0-8c29...).
TIMESTAMP WITH TIME ZONE Data e hora com fuso horário (UTC). Obrigatório em pagamentos. Todo log financeiro precisa de precisão em milissegundos UTC.
BOOLEAN Verdadeiro ou Falso (true / false). Flags de controle interno (ex: is_captured, is_suspicious_fraud).

7.5 Transações e Propriedades ACID em Sistemas Financeiros

Em pagamentos, um único clique do usuário gera múltiplas alterações em banco (ex: debitar R$ 50 da carteira e criar um registro de pedido). Se a energia acabar no meio do caminho, o sistema não pode debitar o cliente sem registrar o pedido. É aqui que entram as propriedades ACID:

  • Atomicidade (All or Nothing): Ou todas as operações acontecem com sucesso, ou nada acontece. Se houver falha, o comando ROLLBACK desfaz tudo.
  • Consistência: Os dados devem respeitar as regras estabelecidas (ex: uma chave primária não pode ser duplicada, um saldo não pode ficar negativo se houver a regra CHECK).
  • Isolamento: Transações simultâneas não interferem umas nas outras antes de serem finalizadas.
  • Durabilidade: Uma vez finalizada com COMMIT, os dados estão gravados de forma permanente no disco.

Bloqueio Pessimista contra Double-Spending (SELECT FOR UPDATE)

Quando dois pagamentos concorrentes tentam gastar o mesmo saldo ao mesmo tempo, o backend utiliza o comando SELECT ... FOR UPDATE. Esse comando bloqueia temporariamente a linha daquele cliente no banco até que o cálculo termine, impedindo que duas requisições leiam o mesmo saldo no mesmo milissegundo.

10. Automação E2E de Pix (BACEN API v2: Cobrança e Devolução)

10.1 Padrões de Identificadores Regulamentados

  • txid: Identificador criado pelo recebedor (26 a 35 caracteres alfanuméricos: ^[a-zA-Z0-9]{26,35}$).
  • e2eid (End-to-End Identification): Gerado exclusivamente pelo Banco Central/SPI na liquidação:
    e2eid = "E" + ISPB (8 dígitos) + Data/Hora UTC (YYYYMMDDhhmm) + Sequencial (11 caracteres)
  • rtrId (Return Identification): Gerado na devolução, iniciado por 'D'.

11. Webhooks: HMAC-SHA256, Desordenamento & Retentativas

11.1 Servidor Receptor Seguro com timingSafeEqual

Para atestar que o payload recebido não sofreu adulteração em trânsito, calculamos a assinatura HMAC-SHA256 sobre o buffer bruto e utilizamos crypto.timingSafeEqual para mitigar ataques de temporização (Timing Attacks).

src/services/SecureWebhookReceiver.tsTypeScript
import http, { createServer, Server, IncomingMessage, ServerResponse } from 'node:http';
import { AddressInfo } from 'node:net';
import { EventEmitter } from 'node:events';
import crypto from 'node:crypto';

export class SecureWebhookReceiver {
  private server: Server;
  private emitter = new EventEmitter();
  public port = 0;
  public url = '';

  constructor(private readonly secret: string) {
    this.server = createServer((req, res) => this.handle(req, res));
  }

  async start(): Promise<string> {
    return new Promise((resolve) => {
      this.server.listen(0, '127.0.0.1', () => {
        const addr = this.server.address() as AddressInfo;
        this.port = addr.port;
        this.url = `http://127.0.0.1:${this.port}/webhook`;
        resolve(this.url);
      });
    });
  }

  private handle(req: IncomingMessage, res: ServerResponse): void {
    const chunks: Buffer[] = [];
    req.on('data', (c) => chunks.push(c));
    req.on('end', () => {
      const rawBody = Buffer.concat(chunks);
      const signature = req.headers['x-signature-sha256'] as string;

      if (!signature) {
        res.writeHead(401).end(JSON.stringify({ error: 'Assinatura ausente' }));
        return;
      }

      const computed = crypto
        .createHmac('sha256', this.secret)
        .update(rawBody)
        .digest('hex');

      const bufExpected = Buffer.from(signature, 'hex');
      const bufComputed = Buffer.from(computed, 'hex');

      if (bufExpected.length !== bufComputed.length || !crypto.timingSafeEqual(bufExpected, bufComputed)) {
        res.writeHead(403).end(JSON.stringify({ error: 'Assinatura invalida' }));
        return;
      }

      const payload = JSON.parse(rawBody.toString('utf-8'));
      this.emitter.emit(`evt:${payload.id}`, payload);
      res.writeHead(200).end(JSON.stringify({ status: 'DELIVERED' }));
    });
  }

  async stop(): Promise<void> {
    return new Promise((resolve) => this.server.close(() => resolve()));
  }
}

14. Kit de Sobrevivência Diário: Debug, Observabilidade & Banco Seguro

Na rotina real de um QA Pleno em pagamentos, o console de testes locais é apenas o ponto de partida. Quando um bug ocorre em homologação ou produção, o erro raramente é evidente. Este capítulo entrega os métodos exatos de investigação e manipulação segura de dados no dia a dia.

14.1 Observabilidade em Produção: Investigando Falhas Reais

Quando um teste automatizado ou manual quebra, o time de engenharia não quer saber apenas que "falhou com 500". Você deve entregar o rastro exato do incidente utilizando ferramentas como Datadog, Kibana (OpenSearch) ou AWS CloudWatch.

A. Como rastrear usando Correlation ID e Trace ID

  1. Ao disparar um teste, copie o valor do cabeçalho X-Correlation-ID enviado ou o id da transação retornado.
  2. Abra a ferramenta de logs (ex: Datadog / Kibana) e filtre pelo campo indexado:
    Kibana / Datadog Search FilterQuery
    correlation_id: "7a9e34b1-8409-42b8-9311-bfad6ce2e104" OR transaction_id: "d3b07384-d113-4f40-8b4e-e0ef3e120899"
  3. Você verá a árvore completa de microsserviços por onde a requisição passou: API Gateway → Microsserviço de Autorização → Motor Antifraude → Adquirente Externa.
  4. Identifique onde a linha do log passou de INFO para ERROR ou WARN.

14.2 De-Para dos Códigos de Retorno das Adquirentes

Quando a adquirente recusa uma transação, ela devolve um código bruto numérico. O gateway mapeia esse código para uma mensagem interna. Tenha esta tabela na sua mesa de trabalho para diagnosticar se a falha é do sistema ou da regra do cartão:

Código Bruto (Cielo / Rede / Stone) Significado Oficial da Bandeira Comportamento Esperado da API Ação do QA
00 ou 000 Transação Aprovada com Sucesso. Status 201 Created, estado AUTHORIZED. Caminho feliz validado.
05 Não Autorizada / Recusa Genérica pelo Banco Emissor. Status 422, código TRANSACTION_DENIED. Validar se o motivo amigável não vaza dados sensíveis ao pagador.
51 Saldo Insuficiente (Limite estourado). Status 422, código INSUFFICIENT_FUNDS. Validar tratamento do erro sem reprocessamento indevido.
57 Cartão Expirado ou Inválido para essa Operação. Status 422, código EXPIRED_CARD. Verificar se a validação prévia de DTO barrou antes de chamar a ponta.
99 ou 999 Timeout de Infraestrutura / Adquirente Indisponível. Status 504 Gateway Timeout ou acionamento de Fallback. Verificar se o Smart Routing chaveou para a adquirente secundária.

14.3 Diretrizes de Segurança em Banco de Dados no Dia a Dia

Como QA Pleno, você terá acesso a bancos de Staging (Homologação) e réplicas de Produção. Um comando errado pode parar a operação da empresa ou apagar registros contábeis. Siga rigorosamente estas regras:

Regra de Ouro: Nunca execute UPDATE ou DELETE direto Em qualquer ambiente compartilhado, sempre abra uma transação manual explícita antes de rodar comandos de alteração. Isso permite inspecionar quantas linhas foram afetadas antes de confirmar.

Como alterar ou limpar dados de teste com segurança absoluta:

Terminal / DBeaver SQL ScriptSQL
-- 1. Inicie a transação manual
BEGIN;

-- 2. Execute a alteração desejada
UPDATE transactions 
SET status = 'VOIDED' 
WHERE idempotency_key = 'test-replay-uuid-881';

-- 3. Verifique o resultado
SELECT id, status, amount_in_cents 
FROM transactions 
WHERE idempotency_key = 'test-replay-uuid-881';

-- 4A. Se alterou APENAS o registro correto:
COMMIT; -- Grava a alteração definitivamente

-- 4B. Se você esqueceu o WHERE ou alterou mais de 1 linha por engano:
ROLLBACK; -- Desfaz TUDO imediatamente como se nada tivesse acontecido!
  • Use Sempre a Read Replica: Para relatórios, extração de massa ou investigação de bugs, nunca conecte no banco principal de escrita (Master/Writer). Conecte na réplica de leitura (Reader) para não onerar o pool de transações dos clientes reais.
  • Evite Lock de Tabelas: Consultas com SELECT * FROM transactions sem LIMIT em tabelas com milhões de linhas geram consumo excessivo de memória e travam threads no banco. Use sempre LIMIT 50 e filtre por índices (ex: created_at >= CURRENT_DATE).

15. Auditoria de PRs, Gestão de Massa & Plano Tático de 60 Dias

15.1 O que Auditar nos Pull Requests (PRs) dos Desenvolvedores

Um QA Pleno atua na prevenção de defeitos antes do merge em develop ou main. Ao ser marcado como revisor no GitHub/GitLab, busque ativamente por estas quatro vulnerabilidades recorrentes:

Ponto Crítico no Código O que Procurar nos Arquivos Alterados Risco Real em Produção Comentário que Você Deve Fazer no PR
Precisão de Moeda Variáveis tipadas como number no TypeScript ou float/double recebendo valores com vírgula (ex: amount = 10.50). Quebra da norma IEEE 754 gerando centavos fantasmas e discrepâncias contábeis no fechamento do dia. "Favor refatorar para utilizar valores inteiros em centavos (`amountInCents`) ou tipo Decimal exato para evitar erros de ponto flutuante."
Concorrência / Saldo Métodos de débito de carteira fazendo apenas SELECT saldo seguido de UPDATE saldo sem lock. Vulnerabilidade a Double-Spending via requisições simultâneas no mesmo milissegundo. "Esta operação de débito precisa de lock pessimista (`SELECT FOR UPDATE`) ou lock distribuído via Redis para evitar race conditions."
Timeouts em Clientes HTTP Instâncias de axios, fetch ou got chamando serviços externos sem propriedade timeout definida. Se a adquirente sofrer instabilidade, as conexões ficam presas indefinidamente até derrubar os containers da API. "Chamada externa sem timeout explícito configurado. Configurar timeout máximo de 5000ms com política de contingência."
Logs e Segurança PCI-DSS Comandos logger.info(req.body) ou console.log gravando payloads brutos de entrada. Vazamento de CVV ou PAN sem máscara nos logs do Datadog/CloudWatch, gerando não conformidade PCI e multas. "O payload impresso nos logs contém dados abertos do cartão. Aplicar sanitização/mascaramento antes de registrar o log."

15.2 Pirâmide de Execução de Testes e Gestão de Massa

Para manter a suíte de testes rápida e sem falsos-positivos (flaky tests), estruture a bateria em duas camadas distintas:

CAMADA 1: Testes de PR (Fast Feedback - 2 a 4 minutos) ├── Executados a cada commit / Pull Request no GitHub Actions ├── Dependências externas 100% mockadas (WireMock ou Mocks locais em Node.js) └── Foco: Contratos (Zod), status codes, validações 400/422, cálculos de Split e regras de negócio CAMADA 2: Testes E2E de Staging / Homologação (15 a 30 minutos) ├── Executados a cada deploy no ambiente de staging ou agendados de madrugada (Nightly) ├── Comunicação real com Sandboxes de Adquirentes (Cielo, Stone) e SPI do Banco Central └── Foco: Transições de estado completas, reconciliação com PostgreSQL e latência real

Gestão Saudável de Massa de Testes

  • Geração Algorítmica de Cartões: Nunca utilize números estáticos em planilhas compartilhadas. Utilize geradores com o Algoritmo de Luhn que forneçam BINs aceitos pelo sandbox configurado.
  • Teardown e Limpeza: Suas fixtures de teste de integração devem conter blocos de cancelamento (afterEach ou rotina dedicada) para cancelar pré-autorizações e expirar cobranças Pix abertas, evitando poluição visual nos dashboards compartilhados de homologação.

15.3 Curso Prático: Roadmap e Evolução do QA Pleno

Com base em feedbacks de estruturação, a abordagem de aprendizado não deve ser assimilar todas as tecnologias simultaneamente. O plano abaixo refina os 60 dias em um roadmap lógico de 8 níveis, garantindo base sólida antes de avançar para arquiteturas complexas.

⭐ Etapa Permanente — Test Design Antes de automatizar, você deve saber quais testes deveriam existir. Para cada endpoint (ex: POST /payments), crie uma matriz contemplando: Happy path, Boundary, Negative, Auth, Authorization, State, Idempotency, Concurrency, Contract, Database, Security, Resilience e Integration. Só depois você automatiza.
Nível Foco do Aprendizado Habilidades & Ferramentas Essenciais
🟢 NÍVEL 1 Base Técnica TypeScript, async/await, Promise, HTTP, JSON, REST, headers, status codes, autenticação e Git. (Sem isso, não avance).
🟢 NÍVEL 2 Playwright API Domínio dos métodos (get, post, etc.), assertions, fixtures, variáveis de ambiente, retries, parallelism e reports.
🟡 NÍVEL 3 Arquitetura Design Patterns: Service Object → Fixture → Factory → DTO → Schema. Saber responder por que uma classe existe e como evitar duplicação.
🟠 NÍVEL 4 API Testing Avançado Comportamento esperado por status (não apenas 200), boundary testing, transições de estado, idempotência e testes de fluxo (ex: Criar → Capturar → Estornar).
🔴 NÍVEL 5 Banco de Dados PostgreSQL: Operações básicas (SELECT, JOIN), constraints, transactions, ACID. Garantir que a API retornou 201 e o banco está consistente.
🔴 NÍVEL 6 Contract Testing Zod, JSON Schema e OpenAPI. Compreender a diferença entre validação TypeScript (compilação) e runtime.
🔴 NÍVEL 7 CI/CD GitHub Actions: Pull Request, Lint, Typecheck, API Tests, Reports, Artifacts e gestão de Secrets.
🟣 NÍVEL 8 Complexidades Reais Webhooks (HMAC, fora de ordem), Resiliência (Toxiproxy, retries), Docker, Observabilidade (Logs, Trace ID, Datadog) e Segurança (OWASP API Top 10).
